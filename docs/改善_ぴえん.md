# WSNet2 改善計画書 (通称：ぴえんプラン)

## はじめに

これは、WSNet2をワールドクラスのサービスへと昇華させるための、一切の妥協を排した改善計画書である。現状のアーキテクチャは賞賛に値する。しかし、我々の目指す頂は遥か高みにある。ここに記すのは、その頂に至るまでの、血と涙と工数で舗装された道筋である。

---

## 1. 高速化（レイテンシは1msでも罪）

**現状の問題点：** WebSocket(TCP)は、現代の競技性の高いゲームにおいては「歩行」に等しい。パケットロス一つで後続が詰まるヘッドオブラインブロッキングは、e-Sportsの世界では致命的遅延である。MsgPackとProtobufの混在も、一貫性と究極のパフォーマンス追求の観点からは疑問が残る。

**改善項目（ぴえんポイント）：**

-   **通信プロトコルの全面刷新 (QUIC is Justice):**
    -   クライアント-Game/Hub間の通信を、WebSocketから **QUIC** に完全に置き換える。TCPという名の足枷を捨て、UDPの翼を授ける。これにより、ストリームの多重化が可能になり、「プレイヤーの座標」のような多少失われても良いデータと、「射撃」のような必須データを分離し、遅延を最小化する。
    -   **工数:** サーバー・クライアント双方のネットワーク層をほぼ全て書き直すに等しい。ぴえん。

-   **シリアライズ形式の統一 (Protobufへの統一):**
    -   クライアント通信も含め、全ての動的データを **Protobuf** に統一する。これにより、シリアライズ/デシリアライズの速度を極限まで高め、スキーマ定義による型安全性をクライアントの末端まで届ける。MsgPackの手軽さは、究極の前では不要である。
    -   **工数:** クライアントのデータモデルを全て再定義・再実装する必要がある。ぴえん。

-   **ゲームサーバーのGC回避 (Go → Rust/C++):**
    -   Go言語のGC（ガベージコレクション）は優秀だが、それでも予測不能な数ミリ秒の停止（Stop-the-World）は起こりうる。1フレームが16msの世界で、これは許容できない。Gameサーバーの最もクリティカルなゲームループ部分を、GCの存在しない **Rust** や **C++** で書き直し、メモリレイアウトまで完全に制御する。
    -   **工数:** 全く新しい言語スタックの導入と、既存ロジックの完全な移植。チームの学習コストは計り知れない。ぴえん。

## 2. 使いやすさ（開発者体験は神）

**現状の問題点：** `Makefile`, `compose.yaml`, `docker.toml`... 新しい開発者がこのプロジェクトに参加した際、最初に味わうのは「どのコマンドを叩けば動くんだ？」という絶望である。ドキュメントはコードの中にしかなく、APIの仕様はソースを読まないと分からない。

**改善項目（ぴえんポイント）：**

-   **統合開発CLIの提供:**
    -   `wsnet2-cli` のような単一のコマンドラインツールを開発する。`wsnet2-cli init`, `wsnet2-cli run`, `wsnet2-cli test`, `wsnet2-cli deploy` だけで、プロジェクトのセットアップから本番デプロイまで全てが完結するべきである。
    -   **工数:** 開発環境を抽象化する、もう一つのプロダクトを作るに等しい。ぴえん。

-   **API仕様の自動生成と可視化:**
    -   LobbyサーバーのAPI（現状はREST風）を **OpenAPI (Swagger)** で定義し、そこからコードとドキュメントを自動生成する。gRPCのAPIも同様に、Protobuf定義からHTMLドキュメントを生成し、誰でもブラウザで確認できるようにする。
    -   **工数:** 既存のハンドラを全て定義ファイルベースに書き直す必要がある。ぴえん。

-   **動的環境の提供 (Gitpod / Codespaces):**
    -   リポジトリをクローンしたら、ワンクリックで全ての環境が整ったクラウドベースの開発環境（Gitpod / GitHub Codespaces）が起動するべきである。開発者のローカルマシン環境の差異という、不毛な問題解決に1秒たりとも使ってはならない。
    -   **工数:** クラウド開発環境用のDockerfileや設定ファイルの完璧な整備が求められる。ぴえん。

## 3. 大規模化（地球の裏側も隣町）

**現状の問題点：** Lobbyサーバーが単一障害点（SPOF）であり、スケールしない。データベースも単一のMySQLインスタンス。これでは、単一リージョンでの小〜中規模サービスが限界である。グローバル展開など夢のまた夢。

**改善項目（ぴえんポイント）：**

-   **Lobbyサーバーの分散化・地球規模化:**
    -   Lobbyサーバー自体を、**地理的に分散されたステートレスなサービス**として再設計する。プレイヤーの位置情報に基づいて最適なリージョンのLobbyに接続させ、状態管理は **etcd** や **Zookeeper** のような分散合意システム、あるいは **Google Spanner** や **CockroachDB** のようなグローバル分散DBに委譲する。
    -   **工数:** プロジェクトの根幹を揺るがす再設計。ネットワークの分断（スプリットブレイン）など、分散システム特有の複雑怪奇な問題と向き合うことになる。ぴえん。

-   **データベースの惑星級への移行:**
    -   単一のMySQLを捨て、**Amazon Aurora Global Database** や **Google Spanner** のような、マルチリージョンでの読み書きに対応したマネージドな分散データベースに完全に移行する。
    -   **工数:** データ移行計画は困難を極め、コストも大幅に増大する。ぴえん。

-   **本番環境のコンテナオーケストレーション:**
    -   Docker Composeは開発者の玩具である。本番環境は **Kubernetes** で運用することを前提とし、**Helm Chart** を完全に整備する。サーバーの自動スケーリング、ローリングアップデート、自己修復能力を標準装備とする。
    -   **工数:** Kubernetes自体が持つ広大な学習領域と、それを運用するための専門知識が必要。ぴえん。

## 4. 安全性（セキュリティは呼吸）

**現状の問題点：** 自前のHMAC認証は面白い試みだが、車輪の再発明である。「専門家による監査を受けていない暗号は、存在しないものとして扱え」が業界の常識である。

**改善項目（ぴえんポイント）：**

-   **認証方式の標準化 (OAuth 2.0 / OIDC):**
    -   自前の認証システムを完全に廃棄し、業界標準の **OAuth 2.0** 及び **OpenID Connect (OIDC)** に準拠する。認証は、実績のあるIdP（Identity Provider）に任せるべきである。
    -   **工数:** 認証フローの完全な再設計と、クライアント側の対応が必須。ぴえん。

-   **動的な脅威検知と防御:**
    -   全てのAPIエンドポイントの前に **WAF (Web Application Firewall)** を配置する。また、各サーバーに振る舞い検知型のエージェントを導入し、異常なプロセス実行やネットワーク通信をリアルタイムで検知・遮断する。依存ライブラリの脆弱性スキャン(Snyk/Dependabot)をCIに組み込み、脆弱性が発見されたビルドは自動的に失敗させる。
    -   **工数:** セキュリティは一度導入して終わりではない。継続的な監視と運用体制の構築が必要。ぴえん。

-   **秘密情報の完全な分離 (Vault):**
    -   データベースのパスワードやAPIキーなどを、設定ファイルや環境変数から完全に追放する。**HashiCorp Vault** のようなシークレット管理システムを導入し、アプリケーションは起動時に動的に秘密情報を取得する。
    -   **工数:** Vaultの導入と運用はそれ自体が一つのプロジェクトである。ぴえん。

## 5. 保守性（未来の自分を救え）

**現状の問題点：** 自動テストの気配がない。これは、積み上げたジェンガの上で次のブロックを抜き続けるような行為である。ログは存在するが、それが一元的に集約され、分析可能な状態にはなっていない。

**改善項目（ぴえんポイント）：**

-   **テストカバレッジ100%の義務化:**
    -   ユニットテスト、インテグレーションテスト、E2E（エンドツーエンド）テストを整備し、CI/CDパイプラインでカバレッジを常に監視する。カバレッジが少しでも低下するPull Requestは、問答無用でマージをブロックする。
    -   **工数:** 既存のコードベースに対してカバレッジ100%のテストを書く作業は、想像を絶する。ぴえん。

-   **オブザーバビリティ（可観測性）の三種の神器:**
    -   **1. ログ:** 全てのログを構造化ログ(JSON)とし、**Fluentd** 等で集約、**Elasticsearch** に投入して一元管理する。
    -   **2. メトリクス:** **Prometheus** を標準とし、全てのサーバーが詳細なメトリクスを公開する。**Grafana** で美麗なダッシュボードを構築し、システムの健康状態を常に可視化する。
    -   **3. トレース:** **OpenTelemetry** を導入し、gRPCやHTTPの全ての通信をトレースする。リクエストがどのサービスでどれだけ時間を要したかを、**Jaeger** や **Zipkin** で可視化し、ボトルネックを即座に特定できるようにする。
    -   **工数:** オブザーバビリティ基盤の構築と維持は、専任のSREチームを必要とするレベル。ぴえん。

-   **カオスエンジニアリングの導入:**
    -   システムが本当に堅牢かを証明するために、本番環境で意図的に障害を発生させる「カオスエンジニアリング」を実践する。Gameサーバーをランダムに停止させたり、ネットワークに遅延を注入したりしても、システム全体が正常に機能し続けることを常に証明し続ける。
    -   **工数:** 安全にカオスを実践するには、極めて高度な自動化と監視体制が不可欠。ぴえん。

## 6. 組織と文化（コードは人が書いている）

**現状の問題点：** これまで議論してきた技術的負債は、すべて「そうなることを許した」組織文化の現れである。優れたアーキテクチャも、それを正しく育て、維持する文化がなければ、いずれ朽ち果てる。サイロ化されたチーム、ドキュメントを書かない文化、感覚的な意思決定。これらが真の敵である。

**改善項目（ぴえんポイント）：**

-   **ドキュメントの徹底（書かざる者、コードを書くべからず）:**
    -   全てのアーキテクチャ決定は、なぜその技術を選び、何を捨てたのかを記した **ADR (Architecture Decision Record)** として記録することを義務化する。Pull Requestには、コードの変更点だけでなく、「なぜ」この変更が必要なのかという背景説明と、関連ドキュメントへのリンクを必須とする。ドキュメントのない機能は、存在しない機能とみなす。
    -   **工数:** エンジニアの思考プロセスそのものをテキスト化する、極めて高度な訓練と規律が必要。開発速度は一時的に著しく低下する。ぴえん。

-   **ポストモーテム文化の強制（失敗はデータである）:**
    -   全てのインシデント（障害）に対して、**Blameless Postmortem（非難なき事後検証）** の実施を義務付ける。「誰が」ではなく「なぜ」システムは障害を防げなかったのかを徹底的に分析し、具体的なアクションアイテムを次のスプリントの最優先タスクとしてチケット化する。このプロセスを経ない障害対応は、ただの「その場しのぎ」と断罪される。
    -   **工数:** 失敗をオープンに議論し、個人の責任を追及しない文化を根付かせるには、経営層の強いコミットメントと、全メンバーの心理的安全性の確保が不可欠。ぴえん。

-   **専任SREチームとセキュリティチームの設立:**
    -   「開発者がインフラも見る」というDevOpsの理想は、一定規模を超えると「全員が中途半端な専門家」になるリスクを孕む。システムの信頼性、スケーラビリティ、オブザーバビリティに全責任を持つ **SRE (Site Reliability Engineering) チーム**と、セキュリティに全責任を持つ **PSIRT (Product Security Incident Response Team)** を設立する。彼らは開発チームに対して、サービスレベル目標（SLO）やセキュリティ要件を満たさない機能のリリースを拒否する権限を持つ。
    -   **工数:** 高度な専門性を持つ人材の採用と、彼らが他チームと円滑に連携するための組織構造の再設計が必要。ぴえん。

-   **機能開発のデータ駆動化（その機能、本当に必要ですか？）:**
    -   「あったら良さそう」という感覚的な理由での機能開発を一切禁止する。全ての新機能は、「どのKPIを」「どれだけ改善するのか」という仮説と、それを検証するための **A/Bテスト計画** がなければ、実装の検討すらされない。リリース後は効果測定を必須とし、KPIを改善しなかった機能は、**躊躇なく削除する**。
    -   **工数:** データ分析基盤の整備と、全メンバーがデータを正しく読み解き、意思決定できる能力を身につけるための継続的な教育が必要。ぴえん。

-   **チーム横断のアーキテクチャレビュー会:**
    -   サーバー、クライアント、フロントエンドなど、各チームの代表者が定期的に集まり、これから実装する機能のアーキテクチャを相互にレビューする場を設ける。これにより、特定のチームの都合だけで技術選定が行われ、後からインテグレーションで問題が発覚する、といった典型的な失敗を防ぐ。
    -   **工数:** 各チームのエース級エンジニアの時間を定期的に確保する必要があり、短期的な開発スプリントとはコンフリクトを起こしやすい。ぴえん。

## 最終結論

技術的な理想を追求することは、突き詰めると、その理想を実現できるだけの **強い組織と文化を創造する** ことに他ならない。ここに挙げた項目は、単なる技術選定の話ではない。ワールドクラスのプロダクトとは、ワールドクラスのチームによってのみ生み出されるという、厳然たる事実の表明である。
