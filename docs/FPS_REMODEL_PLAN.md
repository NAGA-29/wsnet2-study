# WSNet2-FPS 高速化改造計画

## 1. はじめに

本ドキュメントは、既存の `wsnet2` プロジェクトを、低遅延のリアルタイム通信が要求されるFPS（ファーストパーソン・シューティング）ゲームに対応させるための技術的な改造計画を提案するものである。

`wsnet2` は、現状でも中〜大規模の商用利用を想定した、非常に堅牢でスケーラブルなバックエンド基盤である。本計画の目的は、その優れた設計思想（マイクロサービス、スケーラビリティ）を最大限に活かしつつ、FPSの要件を満たすために通信プロトコル層を近代化することにある。

## 2. 現状のプロジェクト規模評価

`wsnet2` は、趣味や学習の範囲を超えたプロフェッショナルなプロジェクトである。

- **開発チーム規模**: サーバーサイド、クライアントサイド、インフラを合わせて、最低でも **4〜5名以上** の専門エンジニアチームを要する規模感。
- **現状の主な用途**: MOBA、セッションベースの対戦ゲームなど、リアルタイム性は求められるものの、TCPベースの通信でも許容可能なジャンル。
- **課題**: 現状のクライアント-サーバー間の主要通信プロトコルは WebSocket (TCP) であり、パケットロスが即座に遅延に繋がるため、ミリ秒単位の応答性が勝敗を分けるFPSには不向きである。

## 3. FPS向け改造計画

FPS化への核心は、**クライアントとGameサーバー間の通信を、TCPベースからUDPベースのプロトコルへ刷新する**ことにある。

### 3.1. 核心課題：通信プロトコルの刷新 (WebSocket → QUIC)

WebSocket (TCP) の最大の問題点は、パケットの順序を保証するために、一つのパケットが失われると後続の全パケットが待たされてしまう「ヘッドオブラインブロッキング」である。

これを解決するため、UDPをベースとした **QUIC (Quick UDP Internet Connections)** プロトコルを導入する。

**QUIC採用のメリット:**
- **低遅延**: TCPのような再送待ちが発生せず、UDPの速度を享受できる。
- **多重化**: 複数のデータ（ストリーム）を並行して送れるため、プレイヤーの移動座標のような多少失われても良いデータと、発砲のような必ず届いてほしいデータを、互いに邪魔することなく送信できる。
- **接続確立の高速化**: TLS 1.3を内蔵しており、暗号化されたセキュアな接続を高速に確立できる。

### 3.2. 改造ステップ

#### ステップ1: Gameサーバー (`wsnet2-game`) の改造

- **リスナーの変更**: WebSocket用のポート (`8000`) を待ち受ける部分を、QUICを待ち受けるように変更、または追加する。Go言語では `quic-go` のような実績のあるライブラリを利用する。
- **ゲームループの修正**: 接続されたクライアントとのやり取りを、WebSocketのコネクションからQUICのストリームに置き換える。信頼性が必要なデータ（イベント）は信頼ストリームで、そうでないデータ（状態同期）は非信頼ストリームで送信するようロジックを修正する。

#### ステップ2: Unityクライアントの改造

- **ネットワークライブラリの置換**: WebSocketライブラリを、C#で利用できるQUICライブラリ（例: `MsQuic.Net`）に完全に置き換える。これはクライアント側のネットワーク層の大部分を書き直すことを意味する。
- **通信ロジックの再設計**: Gameサーバーと同様に、送信するデータの種類に応じてQUICの信頼/非信頼ストリームを使い分けるように実装する。

#### ステップ3: Lobbyサーバー (`wsnet2-lobby`) の役割変更

- **Lobby自体のロジックは変更不要**: マッチング処理などは既存のHTTPベースのままで問題ない。
- **応答内容の変更**: プレイヤーのマッチングが成功した際に、クライアントに返す情報を変更する。
    - **変更前**: `ws://<game-server-ip>:8000` というWebSocketのURL。
    - **変更後**: `udp://<game-server-ip>:<quic-port>` というQUICのエンドポイント情報と、後述する **ワンタイム接続トークン**。

#### ステップ4: 認証フローの変更 (トークンベース認証の導入)

QUICはUDPベースのため、接続してきた相手が本当にLobbyで認証されたプレイヤーかを確認する仕組みが必要になる。

1.  **Lobby**: マッチングが成立すると、暗号学的に安全なワンタイムトークンを生成する。
2.  **Lobby → Client**: 上記で生成したトークンを、QUICのエンドポイント情報と共にクライアントに渡す。
3.  **Lobby → Gameサーバー**: 「このトークンを持ったこのユーザーIDのプレイヤーが接続しに来る」という情報を、gRPC経由で対象のGameサーバーに通知する。
4.  **Client → Gameサーバー**: クライアントは指定されたQUICエンドポイントに接続し、最初のパケットでトークンを提示する。
5.  **Gameサーバー**: 受け取ったトークンがLobbyから通知されたものと一致すれば認証成功とし、通信を開始する。

### 3.3. Hubサーバー (`wsnet2-hub`) の対応

観戦機能も同様に、Watcher（観戦クライアント）とHubサーバー間の通信をWebSocketからQUICに置き換えることで、よりリアルタイムに近い観戦体験を提供できる。

## 4. 改造後のアーキテクチャフロー

プロトコル変更後の、ルーム参加からゲーム開始までのフローは以下のようになる。

```mermaid
sequenceDiagram
    participant C as Client
    participant L as Lobby
    participant G as Game

    C->>+L: POST /rooms/join (HTTP)
    Note over L: プレイヤー認証とマッチング処理
    L->>+G: Assign Player (gRPC)<br/>- UserID<br/>- One-time Token
    G-->>-L: Ack
    L-->>-C: Join Success (HTTP)<br/>- QUIC Endpoint (udp://...)
    - One-time Token

    Note over C: 通信プロトコルをQUICに切り替え

    C->>+G: Connect (QUIC)<br/>- Send One-time Token
    Note over G: トークンを検証し、プレイヤーを特定
    G-->>-C: Connection Established (QUIC)

    Note over C, G: QUICによる低遅延の<br/>リアルタイム通信開始
```

## 5. まとめ

`wsnet2` の堅牢なマイクロサービスアーキテクチャは、FPS化の優れた土台となる。改造の核心は、クライアントとサーバー間の通信プロトコルを **WebSocket (TCP) から QUIC (UDP) へと置き換える**点に集約される。

この改造は、ネットワーク層に特化した大規模な修正となるが、Lobbyサーバーのロジックやサーバー間のgRPC通信など、多くの既存資産を再利用できる。これにより、ゼロから作るよりも遥かに効率的に、大規模な商用FPSにも耐えうるバックエンドシステムを構築することが可能である。
